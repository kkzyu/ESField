## 1. 项目目标

ESField 的目标是验证一种 inference-time site-aware energy guidance：给定蛋白口袋、离线 site map 和预训练 pocket-conditioned 3D flow matching generator，在采样期引导生成分子更好地利用高能水（HEW）候选位点等物理机会。

**当前阶段 (v7)**: 两阶段层次化 Latent Guidance —— 不再试图通过 coordinate-only gradient 微调已有原子位置（v6-D.2 已判为 NO-GO），而是显式拆分生成为 Phase1 (Occupy: 在位点处生长小片段) + Phase2 (Connect: 固定锚原子后生长完整分子)。所有引导能量基于硬编码化学规则（兼容性矩阵），不需要训练。

MVP 阶段只证明方向可行，不声称真实结合自由能提升。核心成功信号是 direct occupancy rate 提升（v7 vs v6-D.2 baseline），同时 validity、QED、SA score 不明显恶化。

## 3. 行为规范

- 先读现有文档和代码，再改文件。
- 每次实现都保持小步提交粒度：一个模块、一个配置、一个测试或一个清晰修复。
- 不把大数据、模型权重、实验输出、临时缓存写进 git。
- 不虚构实验结果。没有真实运行就写"未运行"或"待运行"。
- 不把 docking score 等同于真实 binding free energy。
- 不把 potential network 输出解释成真实物理自由能，只叫 learned compatibility potential。
- 不随意扩大 MVP 范围。新增方法必须先问：是否会影响 MVP 闭环？
- 改需求时先更新文档中的"当前决策"和"任务看板"，再改代码。

## 3.1 语言与输出规范

- 默认使用中文撰写所有协作文档、阶段说明、实验运行记录、任务看板、开发交接、失败分析和最终总结。
- 后续 AI 每完成一个阶段性代码任务，都必须用中文说明：完成了哪些文件、运行了哪些验证、哪些内容未完成、下一步是什么。
- 代码标识符保持英文，包括文件名、类名、函数名、变量名、配置键、CLI 参数和 schema 字段名。
- 代码注释和 docstring 只在有实际帮助时写；涉及 ESField 业务假设、实验风险或非显然逻辑时优先用中文。
- 终端命令、包名、错误栈、日志字段和配置键保持原样，不强行翻译。

## 4. 代码质量要求

- 优先模块化，避免单文件堆积。单个 `.py` 文件目标控制在 300-400 行以内，明显超过时拆分。
- 一个函数只做一件事。函数目标控制在 80 行以内，复杂流程拆成小函数。
- 所有 I/O 路径通过配置或命令行参数传入，不在代码里写死个人路径。
- 数据 schema 用 dataclass / pydantic / typed dict 等结构化方式定义，不用散乱 dict 到处传。
- 配置文件放在 `configs/`，默认 MVP 配置见 `configs/mvp.yaml`。
- 所有可复现实验脚本必须记录输入、输出、配置、随机种子和 git commit。
- 新模块至少有一个轻量 smoke test。没有真实数据时，用 toy fixture 或极小 synthetic example。
- 修改模型采样循环时必须检查显存泄漏风险，避免跨 step 保留计算图。

## 5. 目录约定

当前已创建并实现的代码骨架：

```text
src/

  data/             — atom-site pair 数据（schema、pair builder）
  models/           — 势能网络（atom/site features、potential network、losses）
  training/         — 训练（dataset、train CLI）
  guidance/         — 推断期引导（energy guidance、flow matching hook、lambda schedule、★v7 latent guidance、KTS、two-stage）
  generation/       — 生成器适配（RepMolFlow adapter、baseline CLI、guided generation plan）
  evaluation/       — 评估（site matching、molecule quality、failure analysis）
  visualization/    — 可视化（PyMOL、3D scatter、HTML report）
  utils/            — 基础工具（chemistry、geometry、structure_io）
tests/
  site_detection/
configs/
scripts/
docs/
README/
  editable/         — 可编辑文档（任务看板、开发者文档、运行记录）
  readable/         — 只读参考（研究计划、论文 PDF、skill 定义）
```

大文件策略：

- `data/`、`checkpoints/`、`results/`、`experiments/`、`logs/` 默认不进 git。
- 服务器上推荐用环境变量指定大文件位置：
  - `ESFIELD_DATA_DIR=/data/esfield/data`
  - `ESFIELD_RUN_DIR=/data/esfield/runs`
  - `ESFIELD_CHECKPOINT_DIR=/data/esfield/checkpoints`
- 代码里只保存相对路径或配置键，不保存账号、token、网盘链接密码。

## 6. 运行规范

无卡模式默认允许：

- 写代码。
- 跑单元测试。
- 跑 lint / format。
- 跑小规模 CPU smoke test。
- 解析少量 toy 数据或 1-3 个样例文件。

需要开 GPU 的情况：

- 训练 potential network。
- 跑 flow matching generator。
- 跑 guided sampling。
- 跑大批量 docking / PoseBusters。
- 任何预计超过 10 分钟或占用大量内存的任务。

长任务规范：

- 超过 10 分钟的服务器任务必须使用 `tmux`。
- 启动任务前记录命令、配置、输出目录和预计耗时到 `实验运行记录.md`。
- 任务启动后先观察 1-3 分钟，确认 GPU/CPU/磁盘正常。
- 付费云机长任务必须设置关机或停机提醒。可使用云平台自动关机，或在用户确认后使用 `sudo shutdown -h +N`。
- 任务结束后保存日志、摘要结果和失败原因，然后关机/停机，避免浪费租卡费用。

推荐 tmux 约定：

```bash
tmux new -s esfield_mvp
# run command
tmux detach
tmux attach -t esfield_mvp
```

## 7. Git 与提交规范

当前目录可能是 git 仓库。若未来初始化或进入 git 仓库：

- 每次开始前运行 `git status --short`。
- 不覆盖用户未说明的改动。
- 只提交本任务相关文件。
- 完成一个可运行里程碑后提交一次，例如：
  - `docs: add development handoff templates`
  - `feat: add site map schema`
  - `test: add atom-site pair smoke tests`
- 提交前必须至少运行相关 smoke test；无法运行时在提交信息或开发文档中说明原因。

## 11. 当前风险

- **【最高风险 — v7】Phase 1 成功率未知**：DrugFlow 在 4-atom 小片段生成上的表现未经验证。如果 DrugFlow 在小分子量下生成质量差，Phase 1 可能无法可靠地产出可用锚点。缓解：提高 n_init_atoms 或降低 min_compatibility。
- **【高风险】DrugFlow sample() 多次调用**：v7 需要 Phase 1 重试（≤3 次）+ Phase 2 采样，GPU 显存和耗时增加。需监控。
- **【中等风险】KTS 默认参数过于保守**：α₀=0.01 和 β₀=0.01 仅产生 ~1% 调制，实际效果可能有限。MVP 后可 sweep。
- **【低风险】硬编码兼容性矩阵可能不精确**：当前规则基于化学直觉，未用实验数据校准。后续可替换为训练的小 classifier。
- 数据路径缺失时，代码必须给出清晰错误。
- 位点规则只是 MVP 近似，代码要保留 source/confidence 字段，后续可替换为 WATsite 或更强水位点工具。
